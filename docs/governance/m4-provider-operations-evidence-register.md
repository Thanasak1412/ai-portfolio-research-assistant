## Proposed server-side credential lifecycle

Recommend dedicated environment-scoped secret references: synthetic CI adapter only; ignored local secret injection for an approved optional smoke; separately scoped private-beta server key. [ADR-015](../adr/ADR-015-ed25519-key-ring-and-secret-management.md) already authorizes Railway service-variable secrets for staging/production. Operator/security must approve the provider-specific references, access and lifecycle within existing policy; a different secret-store policy requires separate approval. No default key or fallback to another environment. Limit key access to provider infrastructure; never place it in browser bundles, SSR props, query errors, URLs in logs or diagnostics.

Rotation sequence for owner approval: provision replacement with provider-supported overlap only if confirmed; inject/reload the approved worker; verify a bounded request without raw body/key artifacts; revoke old key; verify revocation and audit safe completion. For suspected compromise revoke immediately and suspend live ingestion; exact incident owner/restart procedure remains to be supplied. Invalid/missing key must fail closed for provider work, not prevent valid M3 ledger commands. Secret-store/infrastructure changes need their existing human authorization.

## Proposed termination/deletion operating procedure

This is a design for owner approval, not permission to execute a destructive operation.

1. Named operator records verified subscription-termination instant, evidence reference and UTC deadline no later than 30 days afterward. Operator/security must name the monitor, acknowledgement/escalation cadence and backup custodian before Phase A closure. Do not infer that unsubscribing signals propagate automatically.
2. Suspend provider retrieval and licensed display immediately on confirmed loss of permission; revoke/inhibit jobs/credentials as appropriate. Do not delete ledger facts or Holdings acquisition evidence to purge provider observations.
3. Inventory all raw/accepted/rejected observations, normalized close records, selected-price references, payloads, staging/retries, replicas, diagnostics, caches, exports (not approved), backups/snapshots and restores. Identify provider-derived data separately; obtain contract-owner interpretation where deletion obligations are unclear, never assume derived copies are exempt.
4. Owner-approved bounded purge procedure tracks each store, cutoff, progress/retries and failures; delete covered data within the deadline. Completion summaries contain counts/safe IDs and evidence references, not reconstructable prices/raw bodies. Missing-store coverage or failed deletion is an incident, not successful completion.
5. Backup/security owner must approve a strategy that satisfies the same deadline: controlled expiry or selective removal plus a restore quarantine/sanitization procedure supported by actual infrastructure. Sanitizing future restores alone is not assumed to permit prohibited data to remain in backups beyond 30 days. If selective deletion/expiry is impossible, resolve provider/legal permission and architecture before activation.
6. Phase B rehearses termination, retries, deadline escalation and restored-snapshot sanitation; proves disabled retrieval/display cannot repopulate deleted data; records completion and sign-off. Operator owns execution, security owns coverage verification. Destructive execution still requires human authorization.

Exact retention/storage rules from the M3 confirmation remain unchanged. This proposal supplies an implementable operating sequence but not deployment proof, new contractual permission or retention duration.

## Proposed invited-user and no-store operating boundary

Recommend server-authoritative invite entitlement checked on every licensed Price/derived-display request and SSR render, separately from bearer identity/Portfolio ownership. Authenticated but uninvited users are denied; revocation prevents subsequent licensed reads/SSR and triggers client memory cleanup under an approved invalidation mechanism. Product/operator must approve admission/revocation records, administrators and enforcement mechanism without quietly redesigning AUTH-v1. Existing public registration remains unchanged and does not confer licensed access.

Recommend `Cache-Control: no-store` on licensed responses and SSR routes; no shared CDN/server cache, persistent browser cache or service-worker storage; React Query memory only and removal on logout/revocation. No localStorage/sessionStorage/IndexedDB licensed data. UI attribution includes the approved dofollow Twelve Data source link; no raw-data public API/export/AI forwarding. Browser back navigation must not be treated as entitlement. How already rendered data is removed during revocation and how HTTP/SSR access is denied need explicit implementation/operating approval and Phase B tests; this proposal makes no claim that deployed controls exist today.
